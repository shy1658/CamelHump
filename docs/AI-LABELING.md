# AI 生成合成内容标识说明 · 显式标识与隐式标识

> **用途**：应用市场上架审核「AI 功能声明」栏的填写底稿；当审核方要求
> 《人工智能生成合成内容标识说明函》时的说明稿底本；以及算法备案咨询时的附件。
>
> **应用**：驼峰 CamelHump · `com.camelhump.app` · v1.1.1
> **依据**：《人工智能生成合成内容标识办法》（国信办通字〔2025〕2 号，2025-09-01 施行）
> **文档版本**：1.0 · 2026-10-30

---

## 一、结论先行

| 标识类型 | 法规依据 | 本应用适用性 | 落地情况 |
| --- | --- | --- | --- |
| **显式标识** | 《标识办法》第四条 | **适用，已实施** | 每条 AI 回复气泡上方带「AI 生成」边框标签；空状态与设置页另有提示 |
| **隐式标识** | 《标识办法》第五条 | **不适用（无适用对象）** | 应用不产生任何生成合成内容文件，无文件元数据可写入隐式标识 |

**一句话**：本应用**只做显式标识，不涉及隐式标识**——因为它从不把 AI 生成内容
写成文件，也从不提供导出/下载/复制功能。

## 二、显式标识：已实施，可直接截图提交

### 2.1 法条要求与实现对照

《标识办法》第四条第一款第（一）项对**文本**类生成合成内容的要求：

> 在文本的起始、末尾或者中间适当位置添加文字提示或者通用符号提示等标识，
> **或者在交互场景界面、文字周边添加显著的提示标识**。

本应用走的是后半句——「在交互场景界面、文字周边添加显著的提示标识」，
即在**每一条 AI 回复气泡的上方**添加独立的标签行。

### 2.2 实现位置与效果

**源码位置**：`entry/src/main/ets/view/ChatView.ets` 第 289–302 行

```ts
Column() {
  // 《人工智能生成合成内容标识办法》要求对 AI 生成内容做显式标识。
  // 审核会索取这张截图，所以标识必须真的出现在界面上，而不是只写在文档里。
  if (msg.role === 'assistant' && !msg.failed) {
    Row() {
      Text('AI 生成')
        .fontSize(9)
        .fontColor(Theme.textFaint)
        .border({ width: 1, color: Theme.border })
        .borderRadius(3)
        .padding({ left: 4, right: 4, top: 1, bottom: 1 })
    }
    .margin({ bottom: 5 })
  }
  ...
}
```

标识的实际呈现：

```
┌─────────────────────────────────┐
│ ┌────────┐                      │   ← 边框标签，非纯文字
│ │ AI 生成 │                      │
│ └────────┘                      │
│ 这是模型生成的回答内容……        │   ← AI 回复气泡
│ 128 tok · 12.4 tok/s            │
└─────────────────────────────────┘
```

**设计考量**：标签用了**边框 + 圆角 + 独立定位**（字号 9pt 偏小但有边框包围），
而不是把「AI 生成」四个字混在正文字里。原因很实际——审核员要在截图里
**一眼看到标识本身**，纯文字容易与回复正文混淆，被判为"标识不显著"。

**实现细节**：标识只在 `role === 'assistant'` 且 `!msg.failed` 时渲染——
用户自己的输入不标 AI，生成失败的消息不标（失败消息不是有效生成内容）。

### 2.3 三处辅助提示（强化告知，非替代）

| 对话页空状态 | 「回复内容由本机模型生成，可能存在错误，请勿直接作为事实依据」 | 首次进入即告知内容性质与免责 |

| 首次运行隐私弹窗 | 「AI 生成的回复在界面上有明确的『AI 生成』标识」 | 首次启动即告知 |

## 三、隐式标识：不适用，理由逐条对应法条

### 3.1 法条原文与拆解

《标识办法》第三条：

> **隐式标识**是指采取技术措施在**生成合成内容文件数据**中添加的，
> 不易被用户明显感知到的标识。

第五条：

> 服务提供者应当……**在生成合成内容的文件元数据中添加隐式标识**，
> 隐式标识包含生成合成内容属性信息、服务提供者名称或者编码、内容编号等制作要素信息。
> ……
> **文件元数据**是指按照特定编码格式嵌入到**文件头部**的描述性信息，
> 用于记录文件来源、属性、用途等信息内容。

### 3.2 适用前提的三个必要条件，本应用**一个都不满足**

隐式标识义务的成立需要同时具备：

```
前提 1：存在「生成合成内容文件」        ← 本应用不产生
前提 2：该文件是服务提供者对外产出的       ← 本应用不产出
前提 3：文件有「头部」，可嵌入元数据       ← 无文件即无头部
```

逐条核查：

| 前提 | 本应用事实 | 核查方式 |
| --- | --- | --- |
| 是否产生生成合成内容**文件** | **否**。AI 回复仅存在于内存中的 `ChatMsg` 对象，随会话结束而销毁，不写盘 | `AppStore.ets` 中 `preferences` 仅写入 `SETTINGS_KEY` 与 `PRIVACY_CONSENT_KEY` 两项，**无对话记录落盘**；`Config.ets` 无任何会话/历史存储键 |
| 是否提供**下载 / 复制 / 导出** | **否**。`ChatView.ets` 中**无复制按钮、无导出按钮、无分享按钮** | 全仓检索 `pasteboard`：仅 `ModelsView`（复制模型下载链接）与 `SettingsView`（复制项目 URL）两处，**均不涉及 AI 生成内容** |
| 是否存在可承载元数据的文件 | **否**。应用写盘的内容只有两类：① 用户导入的 **GGUF 模型文件**（用户自己的第三方文件，非生成合成内容）② `meta.json`（模型清单元数据，记录模型名称/大小/来源路径，**非生成合成内容**） | `ModelRepository.ets` 的 `fs.writeSync` 调用共 2 处，见下表 |

**全部写盘操作清单**（`ModelRepository.ets`）：

| 行号 | 操作 | 写入内容 | 是否生成合成内容文件 |
| --- | --- | --- | --- |
| 132 | `fs.writeSync(dstFile.fd, buffer, ...)` | 复制用户选中的 GGUF 模型文件 | **否**——用户第三方文件的逐字节拷贝 |
| 239 | `fs.writeSync(metaFile.fd, JSON.stringify(meta))` | `meta.json`，模型清单元数据 | **否**——描述模型属性，非 AI 输出 |

### 3.3 关于第四条第二款的补充核对

《标识办法》第四条第二款：

> 服务提供者提供生成合成内容**下载、复制、导出**等功能时，
> 应当确保文件中含有满足要求的显式标识。

本应用不提供上述任何功能，因此该款**同样不适用**。

> 这也说明了一个重要的逻辑顺序：**不是"没做隐式标识"，而是"没有隐式标识的适用对象"。**
> 前者是合规瑕疵，后者是事实描述。审核说明中应当使用后者。

### 3.4 一个必须诚实面对的边界情况

审查者可能提出的追问：**应用内的 `meta.json` 有没有隐式标识？**

回答：**没有，且不需要。** 理由：

1. `meta.json` 的内容是**模型清单元数据**（模型 id、名称、参数量、量化格式、
   文件大小、导入时间、来源 URI），描述的是**用户导入的模型文件**，
   不是 AI 生成的输出；
2. 《标识办法》第五条所规范的"文件元数据"特指**生成合成内容文件的头部标识**，
   目的是让传播平台能识别"此文件是 AI 生成"；
3. `meta.json` 是应用**私有沙箱内的内部索引**，不上传、不分享、不导出给用户，
   也不进入任何传播渠道——即便它带有任何元数据，也不存在被传播平台
   核验的场景；
4. 事实上，AI 生成的回复**从未以文件形式存在过**，何谈给文件打标识。

## 四、若未来增加导出功能，隐式标识必须同步实现

这是一个**前瞻性约束**，写在这里是为了防止合规前提被后续版本静默破坏。

一旦本应用增加"导出对话为文件""保存回复为图片""分享回复"等功能，
以下义务会**立即触发**：

| 义务 | 依据 | 实现要求 |
| --- | --- | --- |
| 文件内含显式标识 | 第四条第二款 | 导出文件中必须含可见的「AI 生成」标识 |
| 文件元数据含隐式标识 | 第五条 | 文件头部写入：生成合成内容属性信息、服务提供者名称或编码、内容编号 |
| 用户服务协议说明标识规范 | 第八条 | 在用户协议中写明标识方法与样式 |

技术实现建议（供后续开发参考）：

- **文本类**：导出为带元数据的文件时，可在文件头写入 `X-AI-Generated: true`、
  `X-AI-Provider: CamelHump` 等自定义头；对通用文本格式可使用 PDF 的
  `Keywords`、PNG 的 `tEXt` 块等标准元数据槽位；
- **图片类**：在 PNG 的 `tEXt`/`iTXt` 块写入标识信息（注意：本仓库现有的
  `docs/store-assets/*.png` **已确认无任何元数据**，符合干净分发要求）；
- **统一要求**：无论哪种格式，**标识信息不得包含用户隐私**（不写用户输入原文）。

> 建议在 `tools/check-repo.sh` 中加入检查项：
> 一旦 `ChatView.ets` 出现 `pasteboard` / 导出 / 分享相关调用，
> 即提示同步实现隐式标识，避免版本迭代时踩空。

## 五、给审核方的说明函（可直接改写提交）

> 以下文本可作为《人工智能生成合成内容标识说明函》底稿。
> 若 AGC 走「二选一」的第一条路径（仅提交显式标识截图），则**不需要**提交本函；
> 本函备用于审核方主动索取的情形。

```
关于《人工智能生成合成内容标识办法》标识措施的情况说明

一、应用基本情况
应用名称：驼峰 CamelHump
包名：com.camelhump.app
版本：1.1.1
应用性质：完全离线的单机应用（端侧大模型运行时）

二、是否涉及 AI 生成合成内容
涉及。应用使用户能够与用户自行导入的开源 GGUF 模型进行本地文本对话，
生成文本类 AI 生成合成内容。

三、显式标识措施
依据《人工智能生成合成内容标识办法》第四条第一款第（一）项，
本应用在交互场景界面中为每一条 AI 生成内容添加了显著的提示标识：
在每条 AI 回复气泡上方添加带边框的「AI 生成」标签。
截图见附件《应用内已添加内容显式标识截图》。
此外，在对话页空状态、设置页「关于」区、首次运行隐私政策授权弹窗中，
均对内容的 AI 生成属性作了明示说明。

四、隐式标识情况
本应用不涉及文件元数据隐式标识，理由如下：
1. 本应用不提供 AI 生成内容的下载、复制、导出功能，
   用户无法将生成内容导出为文件；
2. AI 生成内容仅存在于应用运行期间的内存中，不写入任何文件，
   不产生包含生成合成内容的文件，因而不存在可添加隐式标识的文件元数据；
3. 应用内的文件写入操作仅有两处：复制用户自行导入的 GGUF 模型文件，
   以及写入记录模型属性的清单文件 meta.json。
   二者均非 AI 生成合成内容文件。
综上，本应用不具备《人工智能生成合成内容标识办法》第五条所规定的
隐式标识适用对象，故未实施隐式标识。

五、后续承诺
若本应用后续版本增加 AI 生成内容的导出、下载或分享功能，
将同步依据《标识办法》第四条第二款与第五条，
在导出文件中同时添加显式标识与文件元数据隐式标识，
并依第八条在用户服务协议中补充标识规范说明。

六、联系方式
开发者：shy1658
项目地址：https://github.com/shy1658/CamelHump
```

## 六、核查命令（供第三方复核）

```bash
# 1. 确认无文件导出/复制 AI 内容（应无输出）
grep -n "pasteboard\|export\|share\|saveFile" entry/src/main/ets/view/ChatView.ets

# 2. 确认 pasteboard 仅用于复制链接（结果应只有 ModelsView / SettingsView）
grep -rn "pasteboard" --include="*.ets" entry/src/main/ets/

# 3. 确认全部文件写入点仅 2 处，且均非 AI 输出
grep -rn "fs.writeSync" --include="*.ets" entry/src/main/ets/

# 4. 确认 preferences 不存对话记录（应仅 SETTINGS_KEY 与 PRIVACY_CONSENT_KEY）
grep -rn "store.put" --include="*.ets" entry/src/main/ets/

# 5. 确认无任何字符串常量指向会话/历史存储
grep -rn "SESSION\|HISTORY\|CHAT_LOG" --include="*.ets" entry/src/main/ets/
```
